# YouTube Shorts Cross-Post Pipeline

## Architecture

End-to-end pipeline: M2 has TikTok video outputs → bridge copies via SCP → queues JSON → YouTube Data API v3 uploads.

```
M2:/pipeline/final/*.mp4  --scp-->  /path/to/pipeline\youtube-queue\videos\
                                              |
                                      queue/*.json (auto-created)
                                              |
                              python youtube_api_uploader.py --queue
                                              |
                              YouTube Data API v3 (OAuth 2.0 refresh token)
                                              |
                              /path/to/pipeline\youtube-queue\posted\  ✅
                              /path/to/pipeline\youtube-queue\failed\ ❌
```

**CRITICAL: Do NOT use Playwright browser automation.** Google flags Playwright Chromium as "not secure" during login. The YouTube Data API v3 is the Google-sanctioned approach — no browser automation, no bot detection, no security warnings.

## OAuth 2.0 Setup (One-Time, 5 Minutes)

Before any uploads work, you need a Google Cloud project with YouTube Data API v3 enabled:

1. Go to https://console.cloud.google.com/
2. Create a project (or pick existing)
3. **IMPORTANT: Go to APIs & Services → OAuth consent screen → set to "External" (not "Internal")**
   - If it says "Internal", every login will fail with **"403 org_internal"** — only members of your Google Workspace org can use Internal apps
   - Switch to "External", add your email as a test user. No verification needed for personal use.
4. Enable **YouTube Data API v3**
5. Go to Credentials → Create OAuth 2.0 Client ID → **Desktop app**
6. Download the JSON → save as `/path/to/pipeline\auth\client_secret.json`
6. From Windows PowerShell:
   ```
   python /path/to/pipeline\youtube_api_uploader.py --setup
   ```
   This opens a real Chrome browser window — log in to the Google account that owns the YouTube channel, authorize the app. If it fails with `OSError: [WinError 10048] address already in use`, change the `port=` value in `setup_oauth()` from 8088 to another port (e.g., 8089). A refresh token is saved permanently to `/path/to/pipeline\auth\youtube_token.json`.

After setup, all uploads are **100% silent** — no browser opens, no login prompts, no security warnings. The refresh token auto-renews.

## Running the Bridge

```bash
# Full run — copy latest from M2, queue, and upload via API
python3 ~/income-work/trend-data/youtube_crosspost.py

# Or from WSL via PowerShell:
powershell.exe -Command "python /path/to/pipeline\youtube_crosspost.py"
```

The bridge:
1. **Fetches video list** from M2 via SSH: `find /pipeline/final/*.mp4` sorted by modification time desc
2. **Skips already-processed** — checks `posted/`, `queue/` for duplicates
3. **SCP copies** new videos to `/path/to/pipeline\youtube-queue\videos\`
4. **Auto-creates queue JSON** with title, description, tags
5. **Invokes API uploader** which processes all pending jobs

## Cron Integration

The YouTube Shorts cron (`0 22 * * *`) checks:
1. Does `youtube_token.json` exist? → Yes: run bridge, No: check client_secret.json
2. If client_secret exists but no token: tell user to run `--setup`
3. If neither exists: tell user about Google Cloud Console setup

**COUPLING GATE (was the "BLOCKED" state):** the cross-post pipeline is a *downstream
dependency* of the TikTok channel being LIVE. The bridge only has videos to copy when the
TikTok orchestrator produces new `.mp4` in `/pipeline/final/` — it cannot invent content to
upload. So "cross-post isn't producing anything" almost always means the **TikTok channel is
paused/gated**, NOT a YouTube bug. Re-armed 2026-08-03: cron re-enabled (was disabled during
the TikTok pause) once channel-1 relaunched. When re-arming after any TikTok outage: (1) confirm
the TikTok orchestrator is running + enabled, (2) verify client_secret/token still present,
(3) confirm the channel-1 filter is still set, (4) check `posted/` count isn't stale. Fresh
cross-posts only flow after the live TikTok schedule has actually produced new videos.

## Title Handling — DEFAULT IS BROKEN, USE SIDECAR (2026-07-16)

**The default title is the filename, which is garbage.** `youtube_crosspost.py` / `yt_queue.py` build the
title with `v["name"].replace(".mp4","").replace("_"," ").title()` → "20260715 195953 Evening Ch1".
The real topic ("Why AI PCs are finally worth buying to stop runaway token bills with Bonsai 27B") is generated
by the pipeline but NOT carried to the video by default.

**Fix (already applied to the pipeline):** orchestrator.py writes a `{job_id}.meta.json` sidecar next to each
final `.mp4` on M2 containing `topic`/`hook`/`caption`/`hashtags`/`format`. The cross-post scripts read that
sidecar via `ssh m2 "cat /pipeline/final/{base}.meta.json"` and use `topic` as the title (fallback to cleaned
filename only if no sidecar). See `references/title-sidecar-and-live-edit.md` for the exact code + back-fill
procedure. WARNING: back-filling OLD videos' topics is NOT reliably possible — `content_history.json`
rotates (to a single entry) and `pipeline.log` rotates too, so past topics are usually GONE locally.
For orphaned old uploads, see the ORPHANED VIDEOS note in the --update-titles section below
(user-supplied topic / stopgap filename / leave them).

**To fix titles on ALREADY-UPLOADED videos:** `youtube_api_uploader.py` has `--update-titles` (uses
`videos().update`). It reads each `posted/*.json` (which has `video_id` + Windows `video_path`), fetches the
sidecar topic, and rewrites the live title. Requires the `youtube.force-ssl` scope — see Pitfalls.

**ORPHANED VIDEOS (the real gotcha — hit 2026-07-17):** `--update-titles` ONLY fixes a video if its
M2 sidecar `.meta.json` exists. For uploads that predate the sidecar feature (or where orchestrator never wrote one),
the fixer logs `no sidecar topic (keeping current title)` and SKIPS — it will NOT guess a title. So "wrong title still there"
after a fixer run almost always means **the sidecar is missing on M2**, not a bug in the fixer.
- Verify: `ssh llm-user@m2 "for b in <base1> <base2>; do [ -f /pipeline/final/$b.meta.json ] && echo HAVE $b || echo MISSING $b; done"`
- WHY topics can't be recovered locally (learned the hard way): the skill's older note said "recover from
  `/path/to/pipeline\logs\pipeline.log`" — that is WRONG after rotation. `content_history.json` had been rotated to 1 entry,
  and `pipeline.log` itself rotates (today's log starts fresh; old `[AGENT] Topic:` lines are gone). So old-video topics are
  GONE from local stores. Don't waste time grepping them.
- RECOVERY OPTIONS for the orphans (pick one):
  1. **User supplies the real topics** → write proper sidecars on M2 (`ssh llm-user@m2 "cat > /pipeline/final/<base>.meta.json"`) → re-run `--update-titles`. Best if the videos still get views.
  2. **Stopgap cleaned-filename title** → write a sidecar with `topic` = a humanized version of the filename (e.g. `20260713_083343_morn` → "Morning Update July 13"). Not the real topic, but removes the garbage `20260713_083343_morn_ch1` look. Then `--update-titles`.
  3. **Leave them** → they're 1+ week old, low impact, and all NEW uploads (post-sidecar) already title correctly. The fixer's "already correct, skip" lines confirm the healthy ones.
- CONCRETE CASE (2026-07-17): 5 uploads from Jul 10–13 had no sidecar (predated the sidecar feature) → `--update-titles` logged `no sidecar topic (keeping current title)` for exactly those 5; the other 10 were "already correct". User chose option (c) LEAVE THEM. So: if you see 5 "no sidecar topic" skips on early-July videos, that's expected — don't re-chase. The fix is verified working for everything NEW.
- DO NOT loop `--update-titles` expecting it to invent titles — it won't. The blocker is always missing sidecar metadata, never the fixer code.
- See `references/orphaned-title-recovery.md` for the exact confirm/back-fill commands + why local topic recovery fails after log rotation.

YouTube Shorts title guidance (once you HAVE the real topic):
- Max 100 chars (API truncates silently over that).
- YouTube Shorts: add keyword + emoji + hashtag ("Why AI PCs are worth it 💥 #AI #Shorts").
- TikTok hooks stay short/punchy; YouTube titles can be slightly more descriptive.

## How the API Upload Works

The `youtube_api_uploader.py` uses the Google API Python client:

1. Loads refresh token from `youtube_token.json`
2. Creates `google.oauth2.credentials.Credentials` with auto-refresh
3. Builds a `googleapiclient.discovery.build("youtube", "v3", credentials=...)`
4. Uses `MediaFileUpload` with resumable upload (5MB chunks)
5. Reports progress at 10% intervals
6. Saves video ID + URL to the posted job file

## Failure Recovery

1. Check `youtube-queue/failed/` for error messages
2. Most common issues:
   - OAuth token expired → re-run `--setup`
   - Video file missing → check M2 SCP bridge
   - Quota exceeded → YouTube Data API has 10,000 units/day (1 upload ≈ 1,600 units)
3. If token expired: re-run `--setup` on Windows PowerShell
4. Never re-queue the same video twice — bridge auto-checks `posted/` for duplicates

## SSH from WSL for Bridge

M2 must be reachable as `m2` hostname from BOTH WSL and Windows:

**WSL SSH config** (`~/.ssh/config`):
```
Host m2 gpu-node-2
  HostName gpu-node-2
  User llm-user
  IdentityFile ~/.ssh/id_ed25519
```

**Windows SSH config** (`C:\Users\Admin\.ssh\config`) — MUST match exactly:
```
Host m2 gpu-node-2
  HostName gpu-node-2
  User llm-user
  IdentityFile C:\Users\Admin\.ssh\id_ed25519
  StrictHostKeyChecking no
  UserKnownHostsFile NUL
```

The Windows SSH key must be copied from WSL: `cp ~/.ssh/id_ed25519 /mnt/c/Users/Admin/.ssh/`

## Pitfalls

- **Playwright browser automation is DEAD for YouTube.** Google flags it as "not secure" during login. Use the YouTube Data API v3 instead. The old `youtube_uploader.py` (Playwright) is deprecated.
- **YouTube Data API quota:** 10,000 units/day. Each upload costs ~1,600 units. That's 6 uploads/day max. Pipeline posts 3/day → well within limits.
- **OAuth refresh token can be REVOKED silently** (2026-08-03: a previously-working token returned `invalid_grant: Token has been expired or revoked` after ~2 weeks idle — file still present, 15 prior uploads, yet auth dead). Don't assume "token exists = works". Re-auth with `--setup` and verify with a `channels().list` probe (see Pitfalls).
- **Windows SSH config must match WSL.** The bridge runs `ssh m2` from PowerShell. If Windows SSH config has wrong IP or no key, the bridge fails.
- **Videos are on M2 at `/pipeline/final/`** (which is a symlink to `/data/storage/pipeline/final/`). The bridge SCPs from there.
- **Never call the old Playwright uploader** — it's kept for reference but the crosspost cron now calls the API uploader.
- **Title max 100 chars** for Shorts. The API silently truncates if over.
- **Python on Windows must have google-api-python-client and google-auth-oauthlib installed.** Already installed on this system.
- **If OAuth setup fails with "address already in use"**: port 8080 or 8088 may be occupied. Edit the `port=` parameter in `flow.run_local_server(port=8088, open_browser=True)` inside `setup_oauth()` to an available port.
- **After --setup succeeds, verify immediately**: Run `python /path/to/pipeline\youtube_api_uploader.py --queue` to process any pending queue items. The token file at `/path/to/pipeline\auth\youtube_token.json` should be ~300 bytes of JSON containing `refresh_token`.
- **If you get "403 org_internal"**: Go to OAuth consent screen → switch from "Internal" to "External". Add your email as a test user. No verification needed for personal use.
- **If you logged into the wrong Google account**: delete `/path/to/pipeline\auth\youtube_token.json` and `/path/to/pipeline\auth\youtube_state.json`, then re-run `--setup`. Also clear the youtube-queue/posted/ and youtube-queue/queue/ dirs to reset the skip list.
- **If OAuth token is present but uploads fail with 401**: the refresh token may have been revoked by the user. Re-run `--setup` to get a fresh one.
- **`invalid_grant: Token has been expired or revoked.`** (google.auth.exceptions.RefreshError) — the refresh token is dead even though `youtube_token.json` still exists. A token file present + `posted/` having history does NOT mean auth is live; OAuth tokens get silently revoked (Google policy / long idle). Re-authorize with `python youtube_api_uploader.py --setup` (opens a real Chrome login). **After re-auth, ALWAYS verify the connection** with a `channels().list(part="snippet,statistics", mine=True)` probe — it returns the actual channel title, subscriberCount, and videoCount (e.g. "Budget Build Benchmarks", 1 sub, 15 vids), proving auth + confirming you hit the intended channel. A plain python `urllib`/`curl` probe of api.expo-style endpoints is NOT needed here — build the API client and call `channels().list` for a definitive answer.
- **Live title edits (videos().update) return 403 insufficientPermissions** — the token was granted with ONLY `youtube.upload`. `videos().update` needs `https://www.googleapis.com/auth/youtube.force-ssl`. Add that scope to `setup_oauth()` SCOPES, then the USER must re-run `--setup` once to re-consent. After that `--update-titles` works. (See `references/title-sidecar-and-live-edit.md`.)
- **WINDOWS-PATH TRAP (WSL/Linux Python)**: `os.path.basename("C:\\pipeline\\...\\file.mp4")` on Linux Python returns the WHOLE string (backslashes aren't separators on Linux), so sidecar lookups built from a Windows `video_path` fail. The cross-post runs under Windows Python via `powershell.exe` where backslashes work — but any WSL-side verification script must strip both `/` and `\` (e.g. `re.sub(r".*[\\/]", "", p)`) or call `[System.IO.Path]::GetFileNameWithoutExtension` inside powershell. Don't trust `os.path.basename` on Windows paths from WSL.
